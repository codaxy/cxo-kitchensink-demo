# CxO kitchensink demo

> Is this documentation generated by AI? Yes 🤖 — except this line, which is 100% good old manual labor.

[![Build](https://github.com/codaxy/cxo-kitchensink-demo/actions/workflows/build.yml/badge.svg)](https://github.com/codaxy/cxo-kitchensink-demo/actions/workflows/build.yml)

**CxO** (CxOrchestrator) is a network orchestration platform by [Codaxy](https://www.codaxy.com). It automates
order, service and resource workflows for telecom networks through the TM Forum Open APIs: an order system places a
service order, CxO runs it through workflows written for the operator's network, and keeps the service and resource
inventory current. More at [cxo.codaxy.com](https://cxo.codaxy.com); to get access to CxO, [contact Codaxy](https://cxo.codaxy.com/contact).

Companion code for the **CxO User Guide**. The guide follows one service from design to delivery — Acme Corp
ordering a 1 Gbps Internet connection — and explains each step. This repository has that example as code you can
run against your own CxO environment, and a second, larger one that builds on it.

| Example | What it shows |
|---|---|
| **Acme Internet** (`examples/acme-internet`) | The User Guide, step by step: customer and site, catalog, the worker application, the order, following it by polling or by notifications, inventory, change, activation, removal. |
| **Acme VPN** (`examples/acme-vpn`) | One order for a VPN and three sites. Each item hands its network work to a **resource order**, linked so the order execution shows it, and waits for it without holding a worker. One site fails, the order ends **partial** with the reason from the resource order, and a **retry** resumes only that site. Then the whole VPN is removed. |

Read the guide for the why; use this repository to run it, try changes, and copy from. Everything here calls CxO
through the published CxO API clients on nuget.org, so the code is also a reference for calling CxO from .NET.

## Before you start

You need:

- **git** and the **.NET 10 SDK** — on Windows, macOS or Linux.
- **A CxO environment** you can reach, and either its Keycloak administrator password (for `acme keycloak-client`)
  or a Keycloak client set up as the guide's *Before you start* describes.
- For the order listener and the VPN example, which receive notifications from CxO: **Docker** with Compose, to run
  them next to CxO's reference deployment, or an address of your machine that CxO can reach.

This repository does not bring up CxO itself. CxO's container images are private, so you need an environment from
Codaxy: your organization's own development or test environment, or the reference Docker Compose deployment with access
to the images. For access, or a hands-on demo, [contact Codaxy](https://cxo.codaxy.com/contact).

Use a development or test environment, not production. The examples add their own data there — the Acme customer and
sites, their service and resource specifications with catalog entries and workflow maps, and the orders, services and
resources you run. Setup stops without changing anything if a service specification with one of the examples' names
already exists and is not the example's.

Get the code; every command below runs from the repository's root:

```bash
git clone https://github.com/codaxy/cxo-kitchensink-demo.git
cd cxo-kitchensink-demo
```

The settings in each application's `appsettings.json` default to the addresses of CxO's reference deployment running
on the same machine. For any other environment, override them with environment variables:

| Setting | Environment variable | Default |
|---|---|---|
| TMF API Gateway | `Cxo__GatewayUrl` | `http://localhost:40600` |
| Keycloak token endpoint | `Cxo__TokenUrl` | `http://local.keycloak.codaxy-cxo:8080/realms/Codaxy/protocol/openid-connect/token` |
| Keycloak client | `Cxo__ClientId`, `Cxo__ClientSecret` | `acme-integrator`, none |
| Workflow engine (workers) | `Conductor__BaseUrl` | `http://localhost:48081` |
| Service ordering engine (CLI) | `ServiceOrderingEngine__BaseUrl` | `http://localhost:50211` |
| Service activation (CLI) | `ServiceActivationEngine__BaseUrl` | `http://localhost:50640` |
| Resource ordering engine (VPN CLI) | `ResourceOrderingEngine__BaseUrl` | `http://localhost:50223` |
| Order execution (VPN CLI) | `ServiceOrderingEngine__HttpUrl` | `http://localhost:40211` |
| Keycloak administration (`keycloak-client` only) | `Keycloak__Url`, `Keycloak__Realm`, `Keycloak__AdminUser`, `Keycloak__AdminPassword` | `http://localhost:8080`, `Codaxy`, `admin`, none |

**Keycloak is used at two addresses.** `Cxo__TokenUrl` is where the applications get their tokens. It must be the
exact address the gateway trusts as the token issuer: a token from any other address of the same Keycloak gets `401`.
On the reference deployment that is `http://local.keycloak.codaxy-cxo:8080/realms/Codaxy`; the name resolves through
the hosts entry (`127.0.0.1 local.keycloak.codaxy-cxo`) that the deployment's setup adds, and a token from
`http://localhost:8080` gets `401`. `Keycloak__Url` is only where `acme keycloak-client` signs in as an administrator,
so any address of that Keycloak works there.

**Notifications need CxO to reach your applications.** The order listener and the VPN's worker application receive
notifications from CxO, so CxO must be able to call them. With CxO's reference deployment on your machine, the
simplest way is to run the example applications next to it, inside its Docker network, with Docker Compose:

```bash
docker compose --profile internet up --build                 # Acme Internet: worker application and order listener
docker compose --profile internet up --build acme-listener   # Acme Internet: only the order listener
docker compose --profile vpn up --build                      # Acme VPN: worker application
```

They read `Cxo__ClientSecret` from your environment. For another environment, set `CXO_NETWORK` (the Docker network
CxO's services run in), `CXO_GATEWAY_URL`, `CXO_TOKEN_URL` and `CXO_WORKFLOW_ENGINE_URL` (their addresses inside
that network), or run the applications with `dotnet run` on a machine CxO can reach, as shown below. The
command-line tools always run on your machine.

## Run the Acme Internet example

**1. Create the Keycloak client** the example uses. The CLI creates it with the roles the guide lists (or reuses it)
and prints its secret. It signs in to Keycloak as an administrator, so give it that password; on the reference
deployment it is `admin`:

```bash
export Keycloak__AdminPassword=<keycloak-admin-password>
secret=$(dotnet run --project examples/acme-internet/Acme.Cli -- keycloak-client) && export Cxo__ClientSecret=$secret
```

```powershell
$env:Keycloak__AdminPassword = "<keycloak-admin-password>"
$secret = dotnet run --project examples/acme-internet/Acme.Cli -- keycloak-client
if ($LASTEXITCODE -eq 0) { $env:Cxo__ClientSecret = $secret }
```

If it fails, it prints the reason and exits non-zero, and `Cxo__ClientSecret` is left as it was.

If someone else administers Keycloak, ask them for a client as the guide describes and set `Cxo__ClientId` and
`Cxo__ClientSecret` instead.

**2. Start the worker application** and leave it running. Orders wait until it picks up their work. It only calls
out to CxO, so it can run directly:

```bash
dotnet run --project examples/acme-internet/Acme.Workers
# … Finished deploying conductor definitions (7 tasks, 6 workflows)
```

Or start it with Docker Compose: `docker compose --profile internet up --build` starts it together with the order
listener. Use one or the other, not both, or two worker applications share the work.

**3. Work through the guide** in a second terminal, with `Cxo__ClientSecret` set the same way:

```bash
alias acme="dotnet run --project examples/acme-internet/Acme.Cli --"
# PowerShell: function acme { dotnet run --project examples/acme-internet/Acme.Cli -- @args }

acme setup            # Steps 1-3: customer and site, catalog, workflow maps (safe to run again)
acme order            # Steps 4-5: place the guide's order and follow it to the end
acme show             # Step 6:    the services and resources the order created
acme modify 100       # Step 7:    change the Internet speed
acme deactivate       # Step 7:    switch the service off without an order
acme activate
acme delete           # Step 7:    remove the Internet service, then the CPE
```

The ids each step creates are kept in `acme-state.json` in the current directory.

**Follow orders with notifications** instead of polling (Step 5). The listener registers for order events when it
starts, prints each one as it arrives, reads an order once it is final, and removes its registration when you stop
it. It needs `Listener__CallbackUrl`, the address CxO posts the events to, and does not start without it.

With Docker Compose the address is set for you. If you started the workers with `dotnet run`, start only the listener:

```bash
docker compose --profile internet up --build acme-listener
```

If you started both with `docker compose --profile internet up --build`, the listener is already running; follow it
with `docker compose logs -f acme-listener`.

To run it directly instead, give it an address of this machine that CxO can reach, and allow port 5641 through the
machine's firewall (on Linux, a host firewall commonly blocks containers from reaching host ports):

```bash
export Listener__CallbackUrl=http://<address CxO can reach>:5641/tmf641   # Docker Desktop: http://host.docker.internal:5641/tmf641
dotnet run --project examples/acme-internet/Acme.Listener
```

## Run the Acme VPN example

It uses the same Keycloak client as the Acme Internet example (step 1 above). Its worker application also receives
resource order notifications. Start it with Docker Compose and leave it running:

```bash
docker compose --profile vpn up --build
```

Or run it directly, with an address of this machine that CxO can reach, and the port (5652) allowed through the
machine's firewall:

```bash
export Listener__CallbackUrl=http://<address CxO can reach>:5652/tmf652   # Docker Desktop: http://host.docker.internal:5652/tmf652
dotnet run --project examples/acme-vpn/AcmeVpn.Workers
# … Finished deploying conductor definitions (10 tasks, 9 workflows)
# … Listening for resource order notifications at http://…:5652/tmf652
```

Then, in a second terminal with `Cxo__ClientSecret` set:

```bash
alias vpn="dotnet run --project examples/acme-vpn/AcmeVpn.Cli --"
# PowerShell: function vpn { dotnet run --project examples/acme-vpn/AcmeVpn.Cli -- @args }

vpn setup              # customer and three sites, catalog, both engines' workflow maps; CPEs at HQ and Branch North
vpn order              # the VPN and its three sites in one order — Branch South fails: its CPE is not installed yet
vpn execution          # each item, and the resource order it created
vpn install-cpe south  # register Branch South's CPE
vpn retry              # the order resumes where it stopped: only Branch South runs again
vpn show               # the VPN, its sites, and their resources
vpn delete             # remove the sites, then the VPN
```

`vpn walkthrough` runs all of it and checks each outcome; it starts by making sure Branch South's CPE is not
installed, so it can be run again.

How it is built:

- **Service workflows order resources.** A site's fulfillment orders its attachment on the provider edge and its CPE
  interface as one resource order, linked to the site's order item (`ResourceOrders.Ensure`). The resource ordering
  engine creates the resources and runs the resource workflows: a check that the site's CPE is installed, then the
  configuration.
- **Waiting without holding a worker.** The fulfillment waits with ConductorSharp's SignalWait, and the resource
  order's notification ends the wait. The worker host registers for the state changes of the resource orders it
  created, and when one finishes it reads the order and signals the wait (`ResourceOrderSignals`); a failed one fails
  the wait with the resource order's error, so the reason reaches the service order item. A signal that arrives
  before the workflow starts waiting is kept until it does.
- **Not depending on every notification.** An order finishes even when its notifications cannot be delivered, so the
  worker host also checks the open waits once a minute and signals any whose resource order has finished. The
  example keeps the waits in memory; a production worker host uses a persistent store, so waits survive a restart.
- **Retrying without duplicating.** On a retry the site's fulfillment runs again. It finds the resource order it
  created the first time and retries that one, rather than creating a second order for the same work.

## Where each step of the guide is

| Guide step | Code |
|---|---|
| Before you start | `Acme.Cli/KeycloakClient.cs` (the client), `src/Cxo.Clients` (calling the APIs) |
| 1. Register the customer and the site | `Acme.Cli/Setup.cs`, `RegisterCustomerAndSite` |
| 2. Model the service | `Acme.Cli/Setup.cs`, `ModelTheService` |
| 3. Build the workflows and workers | `Acme.Workers`: `Planning.cs`, `Fulfillment.cs`, `Workflows.cs`, `Program.cs` |
| 3. Map the workflows | `Acme.Cli/Setup.cs`, `MapTheWorkflows` |
| 4. Place the order | `Acme.Cli/Orders.cs`, `GuideOrder` |
| 5. Follow the order | `Acme.Cli/Orders.cs`, `Follow` (polling); `Acme.Listener` (notifications) |
| 6. Find the result in inventory | `Acme.Cli/Inventory.cs` |
| 7. Change the service | `Acme.Cli/Orders.cs` (`Modify`, `Delete`), `Acme.Cli/Activation.cs` |

The guide's *Recommendations* apply to this code as well — for example, every worker here is safe to run twice, and
a modify or delete order carries the whole service.

The example keeps its network planning deliberately simple: it takes the next free VLAN from the resource inventory
and simulates the devices. Real workflows allocate VLANs and similar values with CxO's Resource Manager and configure
devices through their own adapters.
